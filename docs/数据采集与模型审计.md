# 观测数据采集与模型审计

## 为什么需要这个

`npm run audit:prediction` 曾显示模型 ROC AUC 只有 0.597。根因不是算法，
而是标注数据太少太窄：106 条样本、全部来自中国东部少数几座山、正样本占比一度 79%。

社交平台上中外都有大量带地点和时间的云海/晚霞实拍，是最现实的扩样本手段。
`scripts/social-ingest.js` 就是干这个的。

## 合法性边界（请勿放宽）

只走平台**官方公开**接口：oEmbed、公开 REST API、以及用户自备的官方 API key。
**不做**签名伪造、不绕验证码/访客校验、不冒用登录态。

实测确认无法匿名获取的平台已登记在代码的 `BLOCKED` 常量里并附原因，
接入它们的正确做法是让用户自备官方开发者凭据，而不是绕过风控。

## 各平台实测结论

| 平台 | 匿名可达 | 拍摄时间 | 地理坐标 | 说明 |
|---|:--:|:--:|:--:|---|
| **Wikimedia Commons** | ✅ | ✅ EXIF | ✅ | 主力数据源，完全匿名，见下 |
| **Flickr** | 需免费 key | ✅ EXIF | ✅ 精确 | 价值最高，需 `FLICKR_API_KEY` |
| Mastodon | ✅ | ⚠️ 仅发布时间 | ✗ | 靠机位表解析地点，置信度 low |
| YouTube / TikTok / X | ✅ oEmbed | ✗ | ✗ | 只给文案，日期地点需人工补 |
| Instagram | ❌ | | | 需 Facebook App Token |
| 微博 | ❌ | | | 匿名请求跳访客校验，需用户自备 Cookie |
| Reddit | ❌ | | | 公开 JSON 已收紧，需 OAuth |

> X 的 oEmbed 必须用 `publish.x.com`，`publish.twitter.com` 会 301。

## Commons 三种检索模式的取舍

实测数据决定了该用哪种：

- **关键词检索**：命中的 100% 是云海照、100% 带拍摄时间，但只有约 8% 带坐标
- **周边地理扫描**：100% 带坐标，但玉龙雪山周边 132 张里 0 张是云海

所以「先按关键词筛内容、再丢掉没坐标的」远比反过来高效，
`commons-sweep` 即此模式，并用多语种词条覆盖（Commons 贡献者以欧洲/日本居多，
只搜英文会漏掉大半）。

```bash
npm run ingest:commons                    # 多语种深度扫库（推荐）
node scripts/social-ingest.js --source commons --near 30.13,118.17 --radius 10000
node scripts/social-ingest.js --source commons-spots      # 扫机位表全部机位周边
node scripts/social-ingest.js --source mastodon --tag cloudsea
node scripts/social-ingest.js --source flickr --query "sea of clouds"   # 需 key
node scripts/social-ingest.js --source link --url <youtube/tiktok/x 链接>
```

Wikimedia 要求匿名客户端自我节流，脚本内置 1.1s 串行间隔 + 429 指数退避，**不要调快**。

## 数据质量守则

采集器宁可丢样本也不猜：**拿不到坐标或拍摄日期的一律拒绝**。
没有「何时何地」的样本对回测毫无价值，硬塞进去只会污染真值集。

另一个关键防线是 `nearSpot()`：名字命中机位表还不够，坐标也必须对得上才用
机位表的权威高程——否则会把黄山的 1864m 错配到几十公里外的平地样本上。

## 审计结果（682 样本）

```bash
npm run audit:global      # 四面板审计
```

| 面板 | 样本 | 正样本率 | AUC | MCC 最优阈值 |
|---|---|---|---|---|
| A 仅人工标注 | 106 | 79.2% | 0.665 | 50 |
| B A + 控制日负样本 | 274 | 30.7% | 0.597 | **75** |
| C 全球外部（Commons） | 408 | 33.3% | **0.673** | **75** |
| D 全部合并 | 682 | 32.3% | 0.643 | **75** |

> 面板 C/D 的数字含一处生产 bug 修复的收益：`services-core.js` 与 `backtest.js`
> 曾对所有坐标硬编码 `timezone=Asia/Shanghai`，导致境外机位的日出时刻与
> 逐小时数据整体错位（苏黎世实际日出 06:17 被返回成 12:17）。
> 改为 `timezone=auto` 后 C 从 0.668 升至 0.673、D 从 0.641 升至 0.643。
> 国内坐标下 `auto` 同样解析为 Asia/Shanghai，故面板 A/B 数字完全未变。

三条结论：

1. **模型没有过拟合到中国地形。** 面板 C 的地点与人工标注集几乎不重叠
   （欧洲、南美、东南亚，高程 380m~2500m），但表现反而优于面板 B。
   说明判据抓到的是物理规律而不是特定地形气候。

2. **阈值 75 在样本外被独立确认。** 它是在面板 A/B 上定标的，
   却同时是面板 C 和 D 的 MCC 最优点——这是真正的样本外验证。

3. **标注精度本身是主要噪声源。** 面板 C 的正负分离度 9.2 分，明显好于面板 B 的 5.4 分。
   差别在于 Commons 给的是 EXIF 拍摄时间 + 精确 GPS，
   而小红书只有模糊地名（「黄山」）+ 发布时间。
   继续扩样本时应优先选能给出精确时间地点的源。

AUC 0.643 仍低于 0.7 的可用线。下一步不是继续堆样本，
而是排查惩罚项（降水/复合/CAPE）的定标——审计显示它们生效后 AUC 反而略降。

## 四条改进建议的实证检验

有人提出四条提升模型上限的思路。与其凭直觉表态，我们把 682 条样本
拉去做了对照实验。工具链：

```bash
node scripts/feature-lab.js      # 取 D-2~D 三天窗口，提取 22 个候选特征 -> data/features.csv
python scripts/feature-eval.py   # 单特征 AUC / 模型对比 / 决策树结构 / 消融 / 来源偏差
python scripts/feature-recheck.py # 多种子稳健性复核 + 跨源迁移测试
```

之所以要专门写 `feature-lab.js`：现有 `backtest.js` 每次只取单日
（`start_date == end_date`），拿不到"前期降水"这类需要历史窗口的原料。

| 建议 | 实测增量（5 折 CV AUC） | 判定 |
|---|---|---|
| 1a 前期降水（久雨初晴） | **+0.003** | ❌ 证伪 |
| 1b 夜间辐射冷却 | +0.010（种子间波动 ±0.015） | ⚠️ 噪声级 |
| 1c 风向 × 坡向 | +0.007 | ⚠️ 边际，且缺 aspect 数据 |
| 2 浅层决策树替代线性加权 | 0.623 **vs** 逻辑回归 0.677 | ❌ 明确劣于线性 |
| 3 负样本幸存者偏差 | 跨源迁移 AUC **0.516** | ✅ 强力证实，是主因 |

### 1a 前期降水：方向与直觉相反

`precip24` 单特征 AUC **0.433**——低于 0.5 意味着它是**负向**指标，
前期降水越多云海概率越低。为排除"当天在下雨"的混淆，只取当天无降水的
386 条重测：前期无雨 39.3% / 前期小雨 42.9% / 前期中雨 29.6%。
小雨仅 +3.6pp，中雨反而下降。不支持"权重应大幅调高"。

推测原因：能积水到土壤湿透的天气系统，其尾部残云和不稳定层结往往
持续到次日，压过了蒸发量增益。

### 1b/1c 夜间冷却与风向：真实但太小

`nightCooling` 是这批新特征里最有希望的一个（单项 +0.012），物理机制也成立。
但它的增量小于换随机种子造成的波动，在 682 样本下无法与噪声区分。
不是说它没用，是说**现在的数据量证明不了它有用**。
建议样本量翻倍后重测，而不是现在就写进生产判据。

1c 另有个硬障碍：`spot-registry.js` 目前没有 aspect（坡向）字段，
而外部 Commons 样本根本无法补录坡向。做不成全样本验证。

### 2 决策树：被数据明确否决

多种子复核：

| 模型 | 训练集 AUC | 5 折 CV AUC |
|---|---|---|
| 决策树 depth=3 | 0.681 | 0.623 ± 0.010 |
| 决策树 depth=6 | **0.862** | 0.646 |
| 逻辑回归（线性） | 0.689 | **0.677 ± 0.014** |
| 梯度提升 | — | 0.687 ± 0.010 |

depth=6 训练 0.862 / CV 0.646 是教科书级过拟合——树把样本背下来了。
682 条样本撑不起树模型。建议里"准确率会产生质的飞跃"的预期，方向是反的。

顺带一提，depth=3 树的首分裂是 `wind <= 8.7`，其次 `pressure <= 1030.1`，
这恰好印证了现有线性判据里风速权重的合理性。

### 3 幸存者偏差：确实是当前的真瓶颈

这条建议是对的，而且我们把它量化了：

- **用天气特征反推"这条样本来自哪个数据源"，AUC 高达 0.843。**
  也就是说不同来源的样本，天气分布本身就有系统性差异。
- **国内样本训练 → 外部样本测试，AUC 只有 0.516**，基本等于抛硬币。
  反向（外部训练 → 国内测试）0.588，同样很差。

含义是：合并训练得到的 0.687，其中相当一部分性能来自模型
"认出了这条数据是哪来的"，而不是"预测了天气"。这才是 AUC 上不去的根因。

但建议里给的解法（抓景区慢直播/高速监控截图）**合法性与稳定性均未探测**，
不宜直接动手。更稳妥的两个方向：

1. **分域建模**——国内/国外各一套权重，而不是硬合并。
2. 优先扩充能给出精确 EXIF 时间 + GPS 的源，从源头降低分布差异。

### 结论

四条里只有一条（幸存者偏差）触及了真问题。其余三条要么被数据证伪，
要么增益淹没在噪声里。这也是为什么这类建议值得先跑实验再决定——
物理直觉说得通，不等于在真实数据上有增益。
