# 观测数据采集与模型审计

## 为什么需要这个

`npm run audit:prediction` 曾显示模型 ROC AUC 只有 0.597。根因不是算法，
而是标注数据太少太窄：106 条样本、全部来自中国东部少数几座山、正样本占比一度 79%。

社交平台上中外都有大量带地点和时间的云海/晚霞实拍，是最现实的扩样本手段。
`scripts/social-ingest.js` 就是干这个的。

## 合法性边界（请勿放宽）

只走平台**官方公开**接口：oEmbed、公开 REST API、以及用户自备的官方 API key。
**不做**签名伪造、不绕验证码/访客校验、不冒用登录态。

实测确认无法匿名获取的平台已登记在代码的 `BLOCKED` 常量里并附原因，
接入它们的正确做法是让用户自备官方开发者凭据，而不是绕过风控。

## 各平台实测结论

| 平台 | 匿名可达 | 拍摄时间 | 地理坐标 | 说明 |
|---|:--:|:--:|:--:|---|
| **Wikimedia Commons** | ✅ | ✅ EXIF | ✅ | 主力数据源，完全匿名，见下 |
| **Flickr** | 需免费 key | ✅ EXIF | ✅ 精确 | 价值最高，需 `FLICKR_API_KEY` |
| Mastodon | ✅ | ⚠️ 仅发布时间 | ✗ | 靠机位表解析地点，置信度 low |
| YouTube / TikTok / X | ✅ oEmbed | ✗ | ✗ | 只给文案，日期地点需人工补 |
| Instagram | ❌ | | | 需 Facebook App Token |
| 微博 | ❌ | | | 匿名请求跳访客校验，需用户自备 Cookie |
| Reddit | ❌ | | | 公开 JSON 已收紧，需 OAuth |

> X 的 oEmbed 必须用 `publish.x.com`，`publish.twitter.com` 会 301。

## Commons 三种检索模式的取舍

实测数据决定了该用哪种：

- **关键词检索**：命中的 100% 是云海照、100% 带拍摄时间，但只有约 8% 带坐标
- **周边地理扫描**：100% 带坐标，但玉龙雪山周边 132 张里 0 张是云海

所以「先按关键词筛内容、再丢掉没坐标的」远比反过来高效，
`commons-sweep` 即此模式，并用多语种词条覆盖（Commons 贡献者以欧洲/日本居多，
只搜英文会漏掉大半）。

```bash
npm run ingest:commons                    # 多语种深度扫库（推荐）
node scripts/social-ingest.js --source commons --near 30.13,118.17 --radius 10000
node scripts/social-ingest.js --source commons-spots      # 扫机位表全部机位周边
node scripts/social-ingest.js --source mastodon --tag cloudsea
node scripts/social-ingest.js --source flickr --query "sea of clouds"   # 需 key
node scripts/social-ingest.js --source link --url <youtube/tiktok/x 链接>
```

Wikimedia 要求匿名客户端自我节流，脚本内置 1.1s 串行间隔 + 429 指数退避，**不要调快**。

## 数据质量守则

采集器宁可丢样本也不猜：**拿不到坐标或拍摄日期的一律拒绝**。
没有「何时何地」的样本对回测毫无价值，硬塞进去只会污染真值集。

另一个关键防线是 `nearSpot()`：名字命中机位表还不够，坐标也必须对得上才用
机位表的权威高程——否则会把黄山的 1864m 错配到几十公里外的平地样本上。

## 审计结果（682 样本）

```bash
npm run audit:global      # 四面板审计
```

| 面板 | 样本 | 正样本率 | AUC | MCC 最优阈值 |
|---|---|---|---|---|
| A 仅人工标注 | 106 | 79.2% | 0.665 | 50 |
| B A + 控制日负样本 | 274 | 30.7% | 0.597 | **75** |
| C 全球外部（Commons） | 408 | 33.3% | **0.673** | **75** |
| D 全部合并 | 682 | 32.3% | 0.643 | **75** |

> 面板 C/D 的数字含一处生产 bug 修复的收益：`services-core.js` 与 `backtest.js`
> 曾对所有坐标硬编码 `timezone=Asia/Shanghai`，导致境外机位的日出时刻与
> 逐小时数据整体错位（苏黎世实际日出 06:17 被返回成 12:17）。
> 改为 `timezone=auto` 后 C 从 0.668 升至 0.673、D 从 0.641 升至 0.643。
> 国内坐标下 `auto` 同样解析为 Asia/Shanghai，故面板 A/B 数字完全未变。

三条结论：

1. **模型没有过拟合到中国地形。** 面板 C 的地点与人工标注集几乎不重叠
   （欧洲、南美、东南亚，高程 380m~2500m），但表现反而优于面板 B。
   说明判据抓到的是物理规律而不是特定地形气候。

2. **阈值 75 在样本外被独立确认。** 它是在面板 A/B 上定标的，
   却同时是面板 C 和 D 的 MCC 最优点——这是真正的样本外验证。

3. **标注精度本身是主要噪声源。** 面板 C 的正负分离度 9.2 分，明显好于面板 B 的 5.4 分。
   差别在于 Commons 给的是 EXIF 拍摄时间 + 精确 GPS，
   而小红书只有模糊地名（「黄山」）+ 发布时间。
   继续扩样本时应优先选能给出精确时间地点的源。

AUC 0.643 仍低于 0.7 的可用线。下一步不是继续堆样本，
而是排查惩罚项（降水/复合/CAPE）的定标——审计显示它们生效后 AUC 反而略降。

## 博主们靠什么预测云海（以及我们缺了什么）

在动手做负样本之前，先查了中外摄影圈与气象爱好者的经验法则——
他们没有模型也没有数据，却能报得相当准，值得对照。

逐条对上我们的判据：

| 民间/博主判据 | 我们的实现 | 缺口 |
|---|---|---|
| 露点差 ≤2°C（中外一致的头号判据） | `scoreDewPointSpread`，≤1.5°C 给满分 12 | 已覆盖 |
| 清晨相对湿度 >85–92% | `scoreHumidity` | 已覆盖 |
| 风速 1–3 级，风大云散 | 风速项 | 已覆盖 |
| 高压、夜间晴朗无云 | `scorePressure` + 夜间云量 | 已覆盖 |
| 逆温层 | `scoreInversion`（925/850/700hPa 温度） | 已覆盖 |
| 前一日降水 >10–15mm | —— | 已实测证伪（+0.003） |
| **低层(925/850)湿、中层(700)干** | —— | **缺，且无法回测** |
| 「大雾不过三日」持续性效应 | —— | 缺 |

值得注意的是**露点差是中外博主共同的头号判据**，而我们已经给了它 12 分权重，
阈值 1.5°C 也和民间的 ≤2°C 吻合。这算是一次独立的交叉印证。

### 「低层湿、中层干」为什么重要，又为什么暂时做不了

这是唯一一条既没被我们覆盖、物理上又明显成立的判据。它区分的正是
**云海**与**白墙**：低层饱和成云、中层干燥则云顶压不过山头，人站在云上；
若整层都湿，人就埋在云里。

实测 Open-Meteo：

- `forecast` 接口（含 `past_days≤92`）：925/850/700hPa 相对湿度**全部可用**，
  黄山样值 67 / 79 / 38，正是"低层湿、中层干"的形态。
- `archive`（ERA5）接口：压力层变量**全部返回 null**，连温度都没有。

也就是说，**生产可以用，但 682 条历史样本无法回测**。
按"不验证就不写进判据"的原则，这条暂时挂起，
等 METAR 客观样本在 92 天窗口内积累够了再测。

有人提出四条提升模型上限的思路。与其凭直觉表态，我们把 682 条样本
拉去做了对照实验。工具链：

```bash
node scripts/feature-lab.js      # 取 D-2~D 三天窗口，提取 22 个候选特征 -> data/features.csv
python scripts/feature-eval.py   # 单特征 AUC / 模型对比 / 决策树结构 / 消融 / 来源偏差
python scripts/feature-recheck.py # 多种子稳健性复核 + 跨源迁移测试
```

之所以要专门写 `feature-lab.js`：现有 `backtest.js` 每次只取单日
（`start_date == end_date`），拿不到"前期降水"这类需要历史窗口的原料。

| 建议 | 实测增量（5 折 CV AUC） | 判定 |
|---|---|---|
| 1a 前期降水（久雨初晴） | **+0.003** | ❌ 证伪 |
| 1b 夜间辐射冷却 | +0.010（种子间波动 ±0.015） | ⚠️ 噪声级 |
| 1c 风向 × 坡向 | +0.007 | ⚠️ 边际，且缺 aspect 数据 |
| 2 浅层决策树替代线性加权 | 0.623 **vs** 逻辑回归 0.677 | ❌ 明确劣于线性 |
| 3 负样本幸存者偏差 | 跨源迁移 AUC **0.516** | ✅ 强力证实，是主因 |

### 1a 前期降水：方向与直觉相反

`precip24` 单特征 AUC **0.433**——低于 0.5 意味着它是**负向**指标，
前期降水越多云海概率越低。为排除"当天在下雨"的混淆，只取当天无降水的
386 条重测：前期无雨 39.3% / 前期小雨 42.9% / 前期中雨 29.6%。
小雨仅 +3.6pp，中雨反而下降。不支持"权重应大幅调高"。

推测原因：能积水到土壤湿透的天气系统，其尾部残云和不稳定层结往往
持续到次日，压过了蒸发量增益。

### 1b/1c 夜间冷却与风向：真实但太小

`nightCooling` 是这批新特征里最有希望的一个（单项 +0.012），物理机制也成立。
但它的增量小于换随机种子造成的波动，在 682 样本下无法与噪声区分。
不是说它没用，是说**现在的数据量证明不了它有用**。
建议样本量翻倍后重测，而不是现在就写进生产判据。

1c 另有个硬障碍：`spot-registry.js` 目前没有 aspect（坡向）字段，
而外部 Commons 样本根本无法补录坡向。做不成全样本验证。

### 2 决策树：被数据明确否决

多种子复核：

| 模型 | 训练集 AUC | 5 折 CV AUC |
|---|---|---|
| 决策树 depth=3 | 0.681 | 0.623 ± 0.010 |
| 决策树 depth=6 | **0.862** | 0.646 |
| 逻辑回归（线性） | 0.689 | **0.677 ± 0.014** |
| 梯度提升 | — | 0.687 ± 0.010 |

depth=6 训练 0.862 / CV 0.646 是教科书级过拟合——树把样本背下来了。
682 条样本撑不起树模型。建议里"准确率会产生质的飞跃"的预期，方向是反的。

顺带一提，depth=3 树的首分裂是 `wind <= 8.7`，其次 `pressure <= 1030.1`，
这恰好印证了现有线性判据里风速权重的合理性。

### 3 幸存者偏差：确实是当前的真瓶颈

这条建议是对的，而且我们把它量化了：

- **用天气特征反推"这条样本来自哪个数据源"，AUC 高达 0.843。**
  也就是说不同来源的样本，天气分布本身就有系统性差异。
- **国内样本训练 → 外部样本测试，AUC 只有 0.516**，基本等于抛硬币。
  反向（外部训练 → 国内测试）0.588，同样很差。

含义是：合并训练得到的 0.687，其中相当一部分性能来自模型
"认出了这条数据是哪来的"，而不是"预测了天气"。这才是 AUC 上不去的根因。

但建议里给的解法（抓景区慢直播/高速监控截图）**合法性与稳定性均未探测**，
不宜直接动手。

### 补充：我自己提的"分域建模"同样被证伪

既然刚论证过"物理直觉说得通不等于有增益"，那这条推论也得受同样的检验。
做法：固定同一批测试折，对每个域比较 (A) 只用本域训练 vs (B) 用全部数据训练。

| 评测域 | (A) 只用本域 | (B) 全部数据 | 差值 |
|---|---|---|---|
| 国内家族（274 条） | 0.506 ± 0.064 | 0.523 ± 0.077 | −0.017 |
| 外部源家族（408 条） | 0.791 ± 0.046 | 0.789 ± 0.044 | +0.002 |

**没有显著差异，分域建模不值得做。** 跨源迁移差只说明"拿甲域模型直接套乙域"
不行，并不等于"分域训练更好"——分域会让训练量减半，样本损失盖过了分布对齐的收益。

### 真正的发现：瓶颈在国内标签质量，不在算法

上表里更值得注意的是**两个域的绝对水平差了 0.28**：

- 外部源家族（Commons，EXIF 时间 + 精确 GPS）：**0.791**，明显可学。
- 国内家族（小红书模糊地名 + 发布时间 + 控制日弱负标签）：**0.506，等于随机。**

也就是说，国内这批数据里几乎**不存在可学习的信号**。这同时解释了复核 4 里
"用天气特征反推数据来源 AUC 0.843"——两个域的天气分布差异，很大程度上
其实是"一个域有信号、另一个域全是噪声"的投影。

结论随之改变：**继续调算法（换模型、加特征、分域）的收益上限很低，
因为国内这一半数据本身就学不出东西。** 唯一有效的方向是提高标注精度——
拿到精确拍摄时间与坐标，而不是"黄山 + 发帖时间"。
外部源能到 0.791 正是因为它天然满足这个条件。

### 结论

四条建议里只有一条（幸存者偏差）触及真问题，而顺着它查下去，
真正的根因比建议本身更靠前：不是负样本不够，是**国内正负样本的时间地点
精度不足以支撑任何模型**。这也是为什么这类建议值得先跑实验再决定——
物理直觉说得通，不等于在真实数据上有增益；连"实验得出的推论"本身，
也得再跑一次实验才能算数。

### 为什么选 METAR 而不是景区摄像头

建议原文说的是抓景区慢直播/高速监控截图。方向对（要客观、要定时、
不管天气好坏都有记录），但落地方式有三个问题：版权与 robots 立场不明、
画面稳定性无保障、还需要额外做图像识别。

机场 METAR 报文同时满足全部目标，且更硬：

- 每小时定时发报，阴天白墙晴天一条不落 → **天然无幸存者偏差**
- 报文含**云底高度**与分层云量，是观测员/仪器读数，不是"我觉得很美"
- Iowa State Mesonet 存有全球历史存档，可回溯到我们样本的年代
- 完全公开，无需 key，不涉及任何认证绕过
- 是定量物理量，不需要图像识别

核心物理很直接：`云底海拔 = 测站高程 + 云底AGL × 0.3048`，
再与机位高程相比，得到客观三分类——机位在云上（云海）、
云在头顶（阴天）、机位埋在云里（**白墙**）。
白墙这类样本尤其宝贵：它在照片里是失败，在只看湿度的模型里却是高分，
是假阳性的主要来源，而我们此前完全没有。

### 做出来了，规模也够

- 全球站点库 **3915 站**，242 条观测中 **174 条（71.9%）**能匹配到 80km 内测站
- 黄山屯溪（ZSTX，145m）、济南、北京、杭州等国内站都在内
- 扫描 77 个机位近 3 年，产出 **22537 条客观样本**（正 10058 / 负 12479），
  是原始样本量的 33 倍，且完全不依赖"有没有人拍照"

### 但检验发现这批标签不能用

在正式采用前先做了三重检验，结果一致否定：

| 检验 | 结果 | 含义 |
|---|---|---|
| 高程 → 标签 AUC | **0.690** | 标签主要在测"机位有多高" |
| 生产模型全局 AUC | 0.498 | 等于随机 |
| **站内分层 AUC**（高程固定） | **0.494** | 控制高程后仍随机 |
| 各高程带内模型 AUC | 0.427 ~ 0.481 | 每一带都不优于随机 |

正样本率随高程单调上升：<1000m 40.5% → 1000-1500m 41.6% →
1500-2000m 69.5% → 2000-3000m 77.2% → >3000m **93.8%**。
高机位只要天上有云就会被判成"在云上"。

站内分层（高程与地形固定，只剩天气在变）后，单特征也全线失效：
`cloudLow` 0.483、`humidity` 0.491、`dewSpread` 0.502、`wind` 0.459、
`pressure` 0.499。唯一有点信号的是 `cloudMid` 0.410（负向，中层云多则云底高），
物理上讲得通，但它预测的是**机场的云底**，不是山上的云海。

### 失败的真正原因，以及它给出的方向

**天气取自机位坐标，标签取自 20–60km 外的机场。**
云海是山谷局地辐射雾现象，机场多在开阔平地；机场上空的云底高度
不能代表山区的云况。等于在用 A 地的天气预测 B 地的云。

所以问题不在"找不到客观观测源"，而在**客观观测源的位置不对**。

这反过来说明建议 3 原本的直觉在**位置**上是对的：景区摄像头就架在山上，
位置正确，而 METAR 位置错了。用 METAR 替代摄像头是我的判断失误。
若要继续走这条路，必须找**山上**的定点观测，而不是山下的。

数据没有并入训练集。22537 条标签虽然规模诱人，但用高程冒充天气信号，
并进去只会让模型学会"越高分越高"，比没有样本更糟。
脚本与诊断保留在仓库里，是为了记录这条路走不通的**证据**，
省得下次再花一遍力气。`data/metar-sweep.json`（7.7MB）与各缓存
已列入 `.gitignore`，需要时可由脚本重新生成。

## 区分「真云海」与「白墙」：中层云判据

用户提的问题很具体：**有时候只是云雾，并不是真正意义上的云海，能否区分？**

这两者对用户的体验天差地别。真云海是站在云层**上方**俯瞰，白墙是整个人**埋在**云雾里，
能见度几米，什么也拍不到。但在改动之前，评分系统**完全没有中层云的概念**。

### 原来的判据为什么区分不了

`gapToElevation = elevation - cloudBase` 占 25 分，是权重最高的项之一。
问题在于它只算了**云底**，没有云顶：

| 场景 | 云底 | 云顶 | 机位 | gapToElevation | 实际体验 |
|---|---|---|---|---|---|
| 真云海 | 1000m | 1500m | 1860m | 860 | 站在云上，绝景 |
| 白墙 | 1000m | 2500m | 1860m | 860 | 埋在云里，白茫茫 |

两者 gapToElevation **完全相同**。更糟的是白墙场景下湿度 100%(+25)、露点差 0(+12)、
低云量满(+12) 全是加分项，而 `scoreVisibility` 对低能见度**只是不加分、并不惩罚**。
也就是说白墙必然拿高分——这正是用户感受到的「不稳定」。

### 第一个假设被数据否决

直觉上应该建模「云顶 vs 机位高程」的交互。`scripts/whiteout-eval.py` 检验结果：

- 中层云 AUC 在各高程带 0.278 / 0.409 / 0.490 / 0.369，**非单调**
- 高湿子集里高程本身几乎无作用，甚至反向（36.1% → 27.0%）

交互不成立。**又一次印证：物理上说得通不等于数据支持。**

### 成立的是主效应，而且强得罕见

同一批实验里，高湿子集（354 条，恰好是最容易误判的区域）中：

| 特征 | AUC | 对比 |
|---|---|---|
| 中层云量 | **0.319** | 离 0.5 有 0.18 |
| 云层厚度 min(低,中) | **0.311** | 同量级 |
| 夜间辐射冷却 | +0.012 | 噪声级 |
| 前期降水 | +0.003 | 噪声级 |

比之前测过的**任何**候选特征强一个量级。

`scripts/midcloud-calib.py` 定标，成功率单调下降：

| 中层云量 | 云海成功率 |
|---|---|
| 0–10% | 40.3% |
| 25–50% | 22.0% |
| 75–90% | **7.7%** |

### 关键排除：它不是总云量的影子

这是最容易犯的错——新特征其实只是老特征的马甲。实测两者相关系数仅 **0.511**。
控制总云量后（总云量固定在 50–85%）：

- 中层云 < 40%：成功率 **47.1%**
- 中层云 ≥ 40%：成功率 **14.3%**

落差 32.8pp，**独立信号确凿**。

### 物理解释比原直觉更站得住

中层云意味着**系统性锋面云系**，也就是阴天。而真正的云海是**局地辐射雾**，
几乎不伴随中层云。这与前面「前期降水被证伪」是一致的：**天气系统本身就是不利因素**。

一个曾以为漂亮的交叉印证：晚霞模型里中层云是「幕布」，是最大的**正分项**（+28）。
当时写下"同一个变量在两个现象里作用相反，而两边的物理都说得通"。

**但这句话后来被自己的数据推翻了**（见下一节）：晚霞审计显示中层云在晚霞里
同样是负面因素，是晚霞模型的判据写反了。真正的交叉印证是——
**中层云在云海和晚霞两个现象里都不利，因为它代表系统性锋面云系。**
这也再次说明：物理上讲得通的说法，没验证过就不能当结论用。

### 落地结果

`midCloudPenalty`：≤30% 不罚，30→75% 线性 0→12 分，≥75% 满罚 12 分。

审计（CACHE_VERSION 3 → 4）：

| 面板 | 改前 | 改后 | 变化 |
|---|---|---|---|
| C 全球外部 | 0.673 | **0.691** | +0.018 |
| D 全部合并（主参考） | 0.643 | **0.666** | **+0.023** |

+0.023 超出种子波动 ±0.015，**是目前所有改动里增益最大的一个**。阈值 75 仍是最优点。

### 过程中抓到的两个真 bug

1. **`cloud_cover_mid` 没进缓存指纹**——`analyzeDayCloudSea` 会让所有中层云取值
   共用同一条缓存，惩罚在日级路径上**完全失效**（分数纹丝不动）。已补回归测试。
   这个坑代码注释里早有前科记录，新增输入必须同步指纹。
2. **`reasons` 截断到 5 条，白墙警告排在最后被挤掉**。已改为警告优先——
   告诉用户「别白跑一趟」比多说一条锦上添花的好话更有价值。
3. **当前时刻路径漏接**：`analyzeCurrentCloudSea` 没传 `cloud_cover_mid`，
   导致人已经站在山上看实时数据时，警告反而不出现。API 其实早就请求了这个字段，
   只是没用。

## 晚霞模型：第一次被真实数据检验

用户的第二个问题是**晚霞的判断和预测**。查下来发现一个尴尬的事实：
晚霞评分模块（`shared/core/sunset.js`，387 行）逻辑写得很完整，物理讲得也通，
但**全项目只有 1 条晚霞样本，而且 `verified: false`**。

也就是说这个模块从上线起**从未被任何真实数据检验过**。

### 先把样本建起来

复用云海那套 Commons 采集管线，只需换一套多语种检索词
（`sunset glow` / `Abendrot` / `夕焼け` / `火烧云` / `atardecer nubes` …）。
`scripts/social-ingest.js` 的 `--kind glow` 早已支持，缺的只是检索词表。

产出 **85 条**带 GPS + 拍摄日期的晚霞正样本，配 170 条控制日负样本。

采集触顶在 85 条（`no-geo` 丢掉 172 条）。晚霞不像云海局限于少数机位，
但 Commons 上带 GPS 的晚霞照片就这么多。

### 顺带修掉一个致命 bug

`glow-backtest.js` 里还残留着硬编码 `timezone=Asia/Shanghai`。
这对晚霞比对云海更致命——晚霞评分有 20 分**直接来自"相对日落时刻"**，
而样本大量分布在夏威夷、巴黎、新西兰。时区错位十几小时，时间窗得分全废。

另外首轮 255 条里有 115 条取不到天气：晚霞照片多是 2011–2016 年的老片，
超出 `historical-forecast-api` 覆盖范围。加 ERA5 archive 回落后样本拉满到 255 条。

### 第一次审计：AUC 0.566，接近随机

| 指标 | 晚霞 | 云海（对比） |
|---|---|---|
| ROC AUC | 0.566 | 0.666 |
| 正负分差 | 4.2 分 | 9.3 分 |

### 单变量诊断找出病灶

| 特征 | AUC | 现有评分的处理 |
|---|---|---|
| cloudLow | 0.422 | 惩罚 −20 ✓ 方向对 |
| **cloudMid** | **0.457（负向）** | **最大正分 +28** ✗ **方向反了** |
| **cloudHigh** | **0.510（几乎无信号）** | 正分 +18 |

**模型权重最大的一项，方向是错的。** 逻辑回归系数同样给出 cloudMid −0.222。

而且中层云"30–70% 最佳"这一档的实测晚霞出现率是**各档最低**（25.0%）。

这一条与云海侧的结论互相印证：**中层云在两个现象里都是负面因素**，
因为它代表系统性锋面云系（阴天）。此前文档里写的
「中层云在晚霞里是幕布，是漂亮的反向交叉印证」——**被自己的数据推翻了**。

### 先测上界，避免在噪声上调参

这是 METAR 那次的教训。用逻辑回归在同一批特征上做上界估计：

```
现有评分 AUC              : 0.566
逻辑回归 CV AUC（上界估计）: 0.535 ± 0.024
```

**线性上界比现有评分还低**，说明线性调权重毫无空间，改了就是过拟合。

### 但分档表暴露出一个线性看不见的形状

高层云与晚霞是**倒 U 型**，线性 AUC（0.510）完全看不到：

| 高层云量 | 晚霞出现率 |
|---|---|
| 0–10% | 32.4% |
| 30–60% | 47.1% |
| **60–90%** | **60.0%** ← 峰值 |
| ≥90% | 24.1% ← 比晴空还差 |

而旧曲线峰值定在 20–60%，在 60–90% 这个**最好的一档反而在扣分**。

三重检验：

1. 把高层云分箱加进逻辑回归，CV AUC **0.541 → 0.599**，越过现有评分 0.566
2. Bootstrap「30–90% vs ≥90%」落差：**+30.0pp，95% CI [+9.1, +50.7]**，99.7% 为正
3. 这也是我们唯一与 SunsetWx 公开说法吻合的一条——它同样把高层云/高空水汽列为首要因子

### 改动与结果

- `scoreHighCloud`：峰值区间 20–60% → **30–90%**，≥90% 大幅降分（封死天空比晴空更差），权重 18 → **28**
- `scoreMidCloud`：从最大正分 +28 降为轻度负面（≤30% 给 8 分，≥70% 起扣分），权重让给高层云

同口径 bootstrap 对比（其余判据未动，旧总分可精确反推）：

```
旧曲线 AUC 0.539   新曲线 AUC 0.610   提升 +0.071
Bootstrap 95%CI [+0.022, +0.120]   提升>0 占 99.8%
```

正负分差 4.2 → **5.9 分**，MCC 0.128 → **0.189**。

### 一并修掉的问题

- 用户文案还在宣传"中层云是光幕"这个已被证伪的物理，已随判据一起改写
- `scoreMidCloud(null)` 因为 `Number(x ?? 0)` 把缺失值当成 0，落进"中空通透"档**白送 8 分**。
  缺数据必须中性，不能给奖励。已修并加测试。

### 遗留的结构性问题（诚实记录）

晚霞的**基率远高于云海**——云海需要特殊条件，晚霞几乎天天有，只是程度不同。
所以「控制日」作为负样本，对晚霞的标签噪声比对云海大得多，大量控制日其实也有晚霞。

这解释了为什么所有单变量信号都偏弱（最大偏离仅 0.078），也意味着
**0.610 很可能被系统性低估**。要再往上走，需要的是能区分「有晚霞」和
「出彩的晚霞」的**强度标签**，而不是继续在现有标签上调参。
